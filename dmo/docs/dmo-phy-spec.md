## 2. SCH/S: ланцюг кодування [396-2 §8.3.1.1, fig. 9]

Передача: type-1 -> block code -> +tail -> RCPC -> interleave -> scramble. Прийом - у зворотному порядку.

| Крок                                       | Параметри                                | Норма              |
| ------------------------------------------ | ---------------------------------------- | ------------------ |
| type-1                                     | K1 = 60 біт                              | §8.3.1.1           |
| block code (K1+16, K1) = (76,60) -> 76 біт | див. 2.1                                 | §8.3.1.1, §8.2.3.2 |
| tail                                       | 4 біти b2(77..80) = 0 -> type-2 = 80 біт | §8.3.1.1           |
| RCPC rate 2/3                              | 80 -> 120 type-3 біт                     | §8.3.1.1, §8.2.3.1 |
| block interleaver (K,a) = (120,11)         | 120 type-4                               | §8.3.1.1, §8.2.4.1 |
| scrambling                                 | 120 type-5 біт, e(1..30)=0               | §8.3.1.1, §8.2.5   |
| mux                                        | sb(k) = b5(k), k=1..120                  | (41)               |

### 2.1 Block code (K1+16, K1) [396-2 §8.2.3.2]

- M(X) = sum_{k=1..K1} b1(k) X^(K1-k)  (28): b1(1) - старший степінь.
- G(X) = X^16 + X^12 + X^5 + 1  (30) (0x1021 без старшого біта).
- F(X) = [ (X^16 M(X) + X^K1 * sum_{i=0..15} X^i) mod G(X) ] + sum_{i=0..15} X^i  (29). Тобто регістр ініціалізується всіма одиницями (доданок X^K1 * sum X^i) і результат інвертується (доданок sum X^i).
- F(X) = sum f(i) X^i, i=0..15 (31).
- b2(k) = b1(k), k=1..K1; b2(k) = f(K1+16-k), k=K1+1..K1+16 (32). Отже b2(K1+1) = f(15), тобто CRC передається старшим бітом першим.
- "Good residue" для прийому: ітеративний CRC (поліном 0x1021, init 0xFFFF, MSB-first, без фінальної інверсії) по всіх K1+16 бітах дає 0x1D0F. Перевірено скриптом (не декодером): для K1=60 і K1=124 по 200 випадкових повідомлень, кожне закодоване за (28)-(32), результат завжди 0x1D0F. Це збігається з `osmo: crc16_ccitt_bits` + `TETRA_CRC_OK 0x1d0f` (tetra_common.h:69). Саме значення 0x1D0F у стандарті не наведене - виведено обчисленням.

### 2.2 RCPC [396-2 §8.2.3.1.1-§8.2.3.1.3]

- Mother code rate 1/4, 16 станів: вхід b2(k), вихід V(4(k-1)+i), i=1..4, V = sum_{j=0..4} b2(k-j) g(i,j) mod 2, b2(k-j)=0 при k<=j (18)-(19). Початковий стан регістра нульовий (випливає з b2(k-j)=0).
- G1 = 1+D+D^4; G2 = 1+D^2+D^3+D^4; G3 = 1+D+D^2+D^4; G4 = 1+D+D^3+D^4 (20)-(23).
- Puncturing: b3(j) = V(k), j=1..K3, k = 8*((i-1) div t) + P(i - t*((i-1) div t)) (24).
- Rate 2/3: t = 3, P(1)=1, P(2)=2, P(3)=5, i = j (25). Період по V = 8 (2 type-2 біти = 8 біт V, з яких береться 3 type-3 біти).
- Перевірка лічильників (скрипт): K2=80 -> K3=120, всі k унікальні, max k=317 <= 320; K2=144 -> K3=216, max k=573 <= 576.
- Нумерація підпунктів у V1.4.1: 8.2.3.1.3 = rate 2/3, 8.2.3.1.4 = 292/432, 8.2.3.1.5 = 148/432. Вступний текст §8.2.3.1 згадує "1/3" і "8.2.3.1.6" - це редакційна неузгодженість стандарту; для DSB не потрібно.

### 2.3 Interleaver [396-2 §8.2.4.1]

b4(k) = b3(i), i=1..K, k = 1 + ((a*i) mod K)  (33). SCH/S: K=120, a=11 (fig. 9, §8.3.1.1).

### 2.4 Scrambling [396-2 §8.2.5.1, §8.2.5.2]

b5(k) = b4(k) + p(k) mod 2 (36). Див. розділ 4.

## 4. Скремблювання

### 4.1 Норма [396-2 §8.2.5.2]

- Для SCH/S і SCH/H у DSB усі e(1)..e(30) = 0 (на відміну від решти каналів, де e - 30 біт DM colour code).
- Connection polynomial c(x): c_i = 1 для i = 0,1,2,4,5,7,8,10,11,12,16,22,23,26,32 (37)-(38).
- p(k) = sum_{j=1..32} c_j p(k-j) mod 2, k >= 1 (39).
- Ініціалізація (40): p(k) = e(1-k) для k = -29..0; p(-31) = p(-30) = 1.

### 4.2 Початковий стан для e = 0

p(-29..0) = 0, p(-31) = p(-30) = 1. Якщо регістр запам'ятати як 32-бітне слово, де біт N = p(k-(32-N)) (тобто біт 31 = p(k-1), біт 0 = p(k-32)), то p(-31) -> біт 0, p(-30) -> біт 1, решта 0: **init = 0x00000003**.

### 4.3 Звірка з osmo-tetra (читання `src/lower_mac/tetra_scramb.c`, `tetra_scramb.h`)

- `#define SCRAMB_INIT 3` (tetra_scramb.h:14); коментар там же: "BSCH: e(1)..e(30) = 0, p(k)=e(1-k) k=-29..0, p(k)=1 k=-31,-30". **EQUAL**: значення 3 = 0x3 з 4.2.
- `next_lfsr_bit()` (tetra_scramb.c:34): ST(x,y) = lfsr >> (32-y), тапи y = 32,26,23,22,16,12,11,10,8,7,5,4,2,1; новий біт входить у біт 31, зсув вправо. Тобто ST(lfsr,y) = p(k-y), а набір y збігається з j = {1,2,4,5,7,8,10,11,12,16,22,23,26,32} з (38) (**EQUAL**, порівняно списки). Це та сама рекурсія (39), а порядок бітів у слові - як у 4.2.
- `tetra_scramb_get_init(mcc,mnc,colour)` (tetra_scramb.c:87): ((colour | mnc<<6 | mcc<<20) << 2) | 3. Тобто e(1) = біт 31 (старший біт MCC), e(30) = біт 2 (молодший біт colour), p(-31..-30) = біти 0..1 = 1. Відповідає (40). Для DSB `tetra_scramb_get_init` НЕ потрібна: слід викликати `tetra_scramb_bits(SCRAMB_INIT, bits, len)`.
- Додаткова перевірка скриптом (реімплементація логіки C у Python, сам C не запускався): рекурсія (39) з ініціалізацією (40) для e=0 збігається побітово зі зсувним регістром osmo з init=3 на 120 бітах; для 432 випадкових e з init = (e<<2)|3 теж збігається. Перші 32 біти p(k) для e=0: `10111111111101001111000110011010`.
- Що НЕ перевірено: текст EN 300 392-2 §8.2.5.2 (TMO) не читався - у osmo лише коментар про нього; порівняння DMO з osmo зроблено напряму за EN 300 396-2.

- Preamble P3 (l1..l12) [396-2 §9.4.3.3.4, (65)]: `00 01 01 00 01 11` = 000101000111. У osmo-tetra відсутній (osmo бере TMO-бурст без преамбули DMO; жодного P3 у `phy/tetra_burst.c`). Прочитано з рендеру 300 dpi.

  `11 00 00 01 10 01 11 00 11 10 | 10 01 11 00 00 01 10 01 11`
  = 11000001100111001110100111000001100111 (38 біт).

- `f_bits[80]` (burst.c:51): f1..f8=1, f73..f80=1, решта 0 - **EQUAL** з (55)-(57).
- Phase adjustment (hl1, hl2) [396-2 §9.4.3.3.5, table 18]: BN13..14 (offset 12..13). Фаза обирається так, щоб сума фазових переходів символів n1=8 .. n2=126 дорівнювала мінус Dφ пари: Dφ = -sum_{n=n1..n2} Dφ(n) (67); n1=8, n2=126 для hk і hl. Для приймача вміст цих двох бітів не потрібен для декодування; конкретні значення (залежать від Dφ з clause 5) - **UNVERIFIED** (не обчислювались).

## 7. Відкриті питання (потрібен EN 300 396-3, не вгадувати)

1. Розкладка DM-SYNC PDU у 60 type-1 бітах SCH/S (поля, довжини, зміщення).
2. Розкладка DM-SYNC PDU / SCH/H (DM-SYSINFO), що йде в 124 type-1 бітах SCH/H.
3. Виведення DM colour code e(1..30) для не-DSB каналів (з чого складається, як передається).
4. Рахування часу в DM-SYNC PDU: відповідність полів TN/FN/multiframe (кадр 1..18, слот 1..4) і те, що саме несе SYNC.
5. Порядок бітів усередині полів PDU (MSB-first?) і біт-упаковка - не визначено в 396-2.
